# Capability Integration Map

Canonical inventory of Odessay's integration-level capabilities, their real critical chains, and their **actual** test coverage — audited by reading test bodies, not inferring from filenames.

`coverage_status` ages from the moment a new test lands. Update the row in place when that happens instead of re-auditing from scratch — but note the new audit date/commit for that row when you do, so stale data is distinguishable from a wrong audit.

## Why this exists

Odessay has ~2000 unit tests. It still ships bugs at the seams between individually-tested pieces — a component, a service and a persistence layer can each be perfectly tested in isolation while the product breaks the moment they run together for real. This map tracks a third axis that unit-test count doesn't measure:

```text
Code coverage        = what code executes during tests
Contract coverage     = which important boundaries are protected
Capability coverage   = which user/system outcomes are proven across their critical chain
```

This document tracks the third. A capability with many unit tests but no integration proof is still only **partially** covered.

**Relationship to other canonical docs (no duplication — read there first):**
- `workflow/testing/critical-capabilities-testing.md` — canonical owner of the test-level taxonomy (Unit/Contract/Integration/E2E/Performance), the "test at the lowest-cost boundary" principle, and when Playwright is/isn't the right tool. This map does not restate those definitions.
- `workflow/quality/capability-proof-contract.md` — **normative companion of this map.** Holds the MUST rules for *constructing* a proof (production-reachable entry point, real production transition sequence, real internal seams, scheduling ≠ completion, deferred-work ownership, full-contract doubles, swallowed errors, mutation test, status-as-output), the escape taxonomy and the pre-upgrade checklist. This map owns *what* must be proven and *how strong* the evidence is; that contract owns *how* the proof is built. Read it before writing or reviewing any proof.
- `architecture/boundaries.yml` + `tests/architecture/*` — Architecture Contracts (how pieces are *allowed* to relate). This map is the complementary layer: Capability Integration Contracts (what those pieces must *accomplish together*). Architecture tests catch "built the wrong way"; this map catches "every piece looks correct, but the product no longer works."
- `workflow/quality/quality-harness-spec-v2.1.md` — the original Quality Harness spec that started this whole rollout (Phases 1-5 of its §10 shipped close to as-written: PRs #433-#436). This map is **not** what that spec's §8 ("Remediation Plane", `architecture/remediation.yml`) describes — that plan was never built. This map is what got built instead, once the team reached that phase: a different mechanism (per-scenario `coverage_status`, not per-gap `disposition`) that ended up carrying the same "prioritize and close what's structurally weak" responsibility. See the spec's own "Estado de implementación" section for the full accounting of what shipped as planned vs. what diverged.

## Coverage status — exactly one per scenario

```text
NONE                No meaningful automated or repeatable evidence exists.
UNIT_ONLY           Individual pieces are tested, but the integration is not.
CONTRACT            The primary boundary invariant is protected (often with the real
                    collaborator faked on at least one side).
PARTIAL_INTEGRATION A meaningful section of the critical chain is tested with real
                    collaborators; another section is mocked/faked internally.
INTEGRATION         The critical chain is exercised with real collaborators
                    sufficiently to prove the capability (E2E via Playwright counts
                    here when it drives the real app, not a packaged bundle).
RUNTIME             The integration also has evidence in the real Tauri runtime.
RELEASE             Validated as part of the distributed artifact/release process.
```

**Mechanical rule:** `Status` is a single value describing the **whole declared chain**, not the best-covered sub-piece. If one segment of the chain is well-proven and another isn't, the row is `PARTIAL_INTEGRATION` (or lower) — the stronger segment goes in `Note`, never in `Status`. This field has to parse unambiguously for a summary rollup or a future agent to consume it; a status like "CONTRACT (server) / NONE (client)" breaks that.

## Priority model

```text
CRITICAL   Product/data integrity or common high-impact behavior.
HIGH       Important user-facing capability with meaningful integration risk.
NORMAL     Useful coverage but lower expected loss/risk.
```

This first pass follows the spec's own v1 suite plus scenarios this audit found sitting at `NONE`/`UNIT_ONLY` with a real data-integrity, security, or silent-failure risk (flagged `(upgraded)` below). Priority will need revisiting as work proceeds — it is not meant to be precise on the first pass, only directionally right.

(2) `PersistenceCoordinator` — not the caller — owns the durable-content-hash baseline (`getDurableContentHash`/`setDurableContentHash`), advancing it only after a real durable commit (from the write's own authoritative `WritingRecord.contentHash`, itself sourced from the same manifest-sync hash the catalog binding already tracks) and resolving it fresh at the moment each write actually executes, never frozen into a caller's snapshot. (3) `editor-shell.tsx` compares the catalog's live `content_hash` against the coordinator's tracked baseline via `resolveExternalContentChange`, which also filters by `CatalogChange.reason`: only `"bulk"` (the reconciler's own reason) counts as external evidence — the app's own saves emit `"content"`/`"upsert"` for the same document and must never be mistaken for an external edit. CLEAN (no pending local edit) auto-reloads with a brief notice; DIRTY raises a blocking conflict banner (`persistEditorSnapshot` refuses to autosave while it's active) with two explicit actions — "Reload external" / "Keep my version" (the latter re-seeds the baseline to the exact external hash first, then persists normally — no separate force-bypass code path). No automatic merge. **Three real races found and fixed on review, all against the first version of this fix:** (a) the original design threaded a `baselineContentHash` field through `PersistenceSnapshot` itself, frozen at `persist()`-call time — a second save queued behind an in-flight first save would read the *pre-first-save* baseline once it finally ran, misreading its own predecessor's just-landed write as an external conflict and refusing to save (confirmed live: reverting coordinator ownership back to a frozen-snapshot design made the new SEQUENTIAL proof fail with a false `CONFLICT`); fixed by moving baseline ownership fully into the coordinator, resolved fresh at write time. (b) the original design also emitted no `reason` filter, so a document's own normal autosave (`CatalogChange(reason:"content")`) could be mistaken for external reconciliation; fixed by requiring `reason === "bulk"` (confirmed live: removing the filter made 7 decision-function assertions wrongly resolve "conflict"/"auto-reload" for the app's own catalog changes). (c) A third race found on a further review pass: `PersistenceCoordinator.hasPending()` alone under-reports "is there an unsaved edit" — the desktop persistence debounce (150ms rich mode, `MARKDOWN_SAVE_DEBOUNCE_MS` markdown mode) means there is a real window right after a keystroke where the editor already holds an edit that has not reached `persist()` at all yet, so `hasPending()` still (correctly, from its own narrower view) reports nothing pending; an external `bulk` `CatalogChange` arriving in exactly that window would classify the document CLEAN and auto-reload over the unsaved keystroke. Fixed with a second, independent signal — `hasUnconfirmedLocalEditRef`, set the instant a real edit happens (TipTap's own `onUpdate` for rich mode, each markdown-mutating handler's own entry point for markdown mode — never on a programmatic `setContent`, already guarded by the pre-existing `isApplyingContentRef`) and cleared the instant that content is actually handed to `persist()` (from which point the coordinator's `hasUnconfirmedContent()` owns the post-handoff lifecycle, since ODE-627) — combined via a pure `computeHasPendingLocalEdit(shell edit OR coordinator unconfirmed content)` in `external-change-policy.ts` rather than an untested inline logical OR. All three mutation-tested and reverted, zero diff. **Historical scope note (pre-ODE-599; superseded by ODE-599 and ODE-637) — why WATCH-07 was then `PARTIAL_INTEGRATION`:** the write-side guarantee (no silent overwrite, ever) is now fully proven at the real coordinator/service/Rust layer, including both races above. What was *not* yet proven at that time was that `editor-shell.tsx`'s own reactive wiring — a real `CatalogChange` arriving → the real effect calling `getDocumentService().openWriting()` → `editor.commands.setContent()` → the conflict banner's two real button handlers — actually does the right thing when exercised end to end; that would need rendering the full `EditorShell` (or a smaller extracted controller/hook, deliberately not attempted in this pass) and was deferred rather than rushed. At that time, the capability stayed one notch below `INTEGRATION` even though the property it exists to protect (silent data loss) was fully closed at the layer that actually enforced it. **ODE-599 Entrega 2 (movement):** the shell's reaction now lives in `hooks/useExternalDocumentChanges.ts` — the subscription effect and the banner's two handlers moved mechanically (bodies unchanged; state, refs and `persistEditorSnapshot` stay in the shell via `input`, and the hook is called where the effect was, so effect order is unchanged). The same net passes identically (8/8, tests untouched) and two live mutations through the hook (banner set removed; "Keep my version" not persisting) turn the corresponding cases red; the catalog-subscription and per-event read counts are unchanged. **ODE-593 (kept-conflict notice):** `tests/editor-shell-external-changes-desktop.test.tsx` now proves the mounted shell notice against the real filesystem. The race double mirrors Rust's second exchange: external 1 stays at the target, external 2 goes to `.conflict-<id>` (or remains at `.tmp` if `keep_beside` fails), and the user's edit stays only in the editor until choosing `Keep my version`. A→B coverage makes B enter its own conflict and asserts that A's kept-file line is gone; the live mutation removing both `currentWritingId` guards failed because B showed `Carta A con copia.md.conflict-5930abca`. At the time of ODE-593, the row still reported `PARTIAL_INTEGRATION`. **PR #568 (ODE-637 P1)** proves self-write suppression through the real TypeScript command wrappers and mounted shell; **PR #569 (ODE-637 P2)** adds real BLAKE3 content-hash projections and replays a same-path, same-inode external edit through Rust/SQLite, checking the persisted binding hash against disk over a fresh SQLite connection. ## Phase 3 — Critical Proofs: methodology

Writing a capability integration test is not "convert the scenario row into a test file." Follow this sequence, and produce the Proof Contract *before* writing any test code:

> **Normative companion — read before BUILD or REVIEW of any proof:** `workflow/quality/capability-proof-contract.md`. This section explains the method; that contract holds the MUST rules the Phase 3 PRs showed are not obvious from the method alone — production-path fidelity, scheduling ≠ completion, deferred-work ownership, full-contract doubles, swallowed errors, and **coverage status as an output, never a goal** — plus the escape taxonomy (`MOCKED_SEAM`, `WRONG_ASSERTION`, `NON_PRODUCTION_PATH`, `STALE_PROOF`, `ARCHITECTURE_GAP`) and the pre-upgrade checklist.

```text
Capability Scenario
  → Proof Contract (Property, Real collaborators, Allowed fakes, Given/When/Then, Failure/Then,
                    Production path: entry point + preceding transitions that reach Given,
                    Completion event: the exact point after which the invariant holds)
  → pick the minimum-sufficient runtime (Vitest by default; cargo test for the
    Rust/SQLite seam; a local Postgres/pgTAP for RLS/DB-function properties;
    Playwright only when the property genuinely lives in the DOM)
  → implement the test
  → mutation-test it: reintroduce the exact bug the property guards against,
    confirm the test goes red for that reason, then revert
  → run the pre-upgrade checklist (capability-proof-contract.md), THEN derive
    the status — the status is a conclusion of the evidence, never the target
  → update this map's coverage_status/Evidence/Note for every scenario the
    test closes (one test can legitimately close several IDs)
```

**Runtime is chosen by where the real integration lives, not by convention.** Vitest is the default and can express unit, contract, *or* integration proofs — what determines the level is which collaborators stay real, not which runner executes it. Reach for `cargo test` (real fs + real SQLite) when the property is specifically about the Rust side; a local Postgres/pgTAP harness when the property lives inside a database function or RLS policy (a Vitest mock of Supabase cannot prove either); Playwright only for properties that genuinely depend on DOM/browser choreography (scroll, focus, keyboard, drag) — and even then, try to separate the *ownership* logic (Vitest) from the *DOM mechanics* (Playwright, scoped) rather than handing the whole capability to Playwright.

**A capability test is good exactly when: if you reintroduce the failure mode it exists to prevent, it fails for the right reason.** Passing today proves nothing on its own. Five supporting checks:
1. Assert observable end-state (file content, catalog resolution, a rendered projection) — not `toHaveBeenCalled()` on the pieces you're supposed to be trusting.
2. The collaborators the *declared chain* names are real, not mocked — a real `DocumentService` calling a mocked catalog and a mocked filesystem is still `CONTRACT`, not `INTEGRATION`, no matter how good the mocks are.
3. The test crosses the boundary where bugs actually appear (the seam), not just one side of it.
4. Failure/race variants exist when that's the actual risk — happy-path-only is insufficient for anything persistence-shaped.
5. The test is deterministic — no `sleep`, no real external API, no shared/production state; temp dirs, deferred promises, and deterministic fakes only at genuinely external boundaries.

**Formal bar for declaring `INTEGRATION` (all seven, or the row stays `PARTIAL_INTEGRATION`):**
```text
1. The relevant entry point of the declared critical chain actually executes.
2. The chain's internal collaborators are real, not mocked/spied.
3. Only genuinely external boundaries are faked (network, third-party providers) —
   never an internal collaborator the chain names.
4. Observable state/artifact is verified, not just that functions were called.
5. The identified failure mode would make the test fail if reintroduced —
   verified live, not assumed.
6. The starting state is reached through the transitions production actually
   performs — not seeded — whenever those transitions can touch the property
   (otherwise the escape is NON_PRODUCTION_PATH).
7. The assertion runs after the event that establishes the invariant, not the
   one that schedules it; no error inside the chain was swallowed by production
   during the run.
```

**Test organization is by capability, not by source file** — `tests/integration/<capability-area>/<scenario-cluster>.test.ts` (e.g. `tests/integration/documents/materialize-save-reopen.test.ts`), so the unit of thought stays "what does the product need to keep doing," not "which class am I testing." One well-chosen test can legitimately close several scenario IDs at once (see DOC-03/DOC-04 below) — that's a feature, not scope creep, as long as each closed ID's Proof Contract is genuinely satisfied.

1. `editor-shell.tsx`'s `exportBinary()` returned bare `undefined` (not `false`) on its `!currentWritingId` early return — a real contract violation of "success only if written," but **latent**: the PDF/DOCX menu items are `disabled={!hasRemoteWriting}`, and `hasRemoteWriting` requires the same `writingId` truthy in the same render, so the branch is provably unreachable via the main editor's own UI today. Fixed anyway (`return false`) as defense-in-depth against a future caller without that guard. Mutation-tested live: reverting to a plain `return` reproduced the false-success text in `properties-panel-export.test.tsx`'s regression test.
2. `PropertiesPanel.handleExport`'s own guard was inverted relative to the invariant: `if (exported === false) return` shows success unless explicitly `false`, but the prop type (`Promise<boolean \| void>`) permits `void` — so a caller resolving `void` (not just the two booleans) would wrongly show success. Fixed to `if (exported !== true) return` (opt-in to success). Mutation-tested live: reverting to the `=== false` check reproduced the same false-success text.
3. Investigating whether the same invariant held at *every* call site (not just the one named in the original Proof Contract) surfaced a **third, independently reachable** instance, in both its export formats: `app/(app)/desk/page.tsx`'s `exportWritingDocument` called `await saveBinaryArtifact(result.data)` with no `return`, discarding the boolean; `downloadWritingMarkdown` (in both `desk/page.tsx` and `collections-view.tsx`, which share the same bug) returned nothing on its own early-return-when-no-payload branch either. `WritingPreviewModal.handleExportDocument`/`handleExportMarkdown` had no branch distinguishing cancel from success at all, showing "PDF exported."/"DOCX exported."/"Markdown exported." on any non-throwing resolution. Unlike bug 1, this is reachable via a normal click in Desk's own preview modal (not gated the way the main editor is) — for PDF/DOCX and for Markdown alike. Fixed the same way as bug 2, for all four functions: each now returns the boolean explicitly, `WritingPreviewModal`'s `onExportDocument`/`onExportMarkdown` prop types widened to `Promise<boolean \| void>`, `handleExportDocument`/`handleExportMarkdown` both gained the identical `!== true` guard. Mutation-tested live on the `saveBinaryArtifact` dispatch hop (reverting the desktop branch to discard the boolean reproduced a false `true`); the `WritingPreviewModal` handlers themselves could not be mutation-tested live — see the scope note below.

**Scope note — why this stays `PARTIAL_INTEGRATION`, not `INTEGRATION`:** two real gaps, not one.
- **The internal seam between the Desk caller and the proven `saveBinaryArtifact` layer is still faked — the same rule applied to AI-01.** The editor half is closed: since ODE-601, `tests/editor-shell-export-delivery-desktop.test.tsx` mounts the real `EditorShell` in desktop mode and drives the real `exportMarkdown`/`exportBinary` → real `DesktopDocumentService.exportWriting` → real `saveBinaryArtifact` → real `saveDesktopBinaryExport` → native boundary fake, with only the last hop faked. The Desk half is not: `export-delivery.test.ts` proves `saveDesktopBinaryExport`/`saveBinaryArtifact` against a real fs, but `desk/page.tsx`'s `exportWritingDocument`/`downloadWritingMarkdown` (and `collections-view.tsx`'s `downloadWritingMarkdown`), which feed `WritingPreviewModal`, are never exercised as real callers into that layer. The declared remaining gap: `real Desk caller (exportWritingDocument/downloadWritingMarkdown) → real export orchestration → saveBinaryArtifact → saveDesktopBinaryExport → native boundary fake`. Not closed yet: those callers are closures inside a large page component, not extractable without a larger refactor judged out of scope here.
- **`WritingPreviewModal`'s own fix (bug 3, all four affected functions/formats) has no DOM-level test of its own.** Driving this component past a real click into `await`ed settlement hits a reproducible `act()` hang, confirmed independent of this change (reproduces identically with a trivial `vi.fn().mockResolvedValue(true)` fake, and independent of whether `preview` is null or populated — ruling out both the earlier `hasRemoteWriting` hypothesis and an unrelated mock-identity bug found and fixed along the way in `useWritingPreviewCache`'s test double). `preview-modal.test.tsx` never surfaces this today because it never drives a click.
