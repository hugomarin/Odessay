## Paso 3 — Loop de supervisión

```
orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 900000 --json
```

Por cada delivery que llegue:

1. Si es `question`/`escalation`: respóndela con `orca orchestration reply --id <message_id> --body "<respuesta>" --json` si puedes resolverla sin riesgo; si requiere decisión de producto o de arquitectura, NO la resuelvas: repórtala a Hugo en tu salida y deja el worker en espera.
2. Si es `worker_done`: valida contra el Dispatch activo. Verifica el PR con `gh pr list --state all --search "ODE-XXX" --limit 5 --json number,state,url`. Luego decide el recurso: `orca orchestration worker-release --dispatch <dispatch_id> --json` (o `worker-retain` solo si Hugo pidió conservarlo).
3. Actualiza el comment del worktree: `orca worktree set --worktree name:ode-XXX-build --comment "<estado corto>" --json`.
4. Acusa el delivery: `orca orchestration check --ack <delivery_id> --wait --types "worker_done,escalation,question" --timeout-ms 900000 --json`.
5. Sigue esperando hasta que los workers esperados se hayan asentado.

Cada vez que el `check --wait` termine por timeout (sin delivery), haz un barrido de gates (Paso 4) antes de volver a esperar. Un timeout no es fallo.
