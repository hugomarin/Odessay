## Release wiring: brechas comprobadas y propuesta concreta

- `blocking-ci.yml` agrega quality (typecheck/lint/`npm test`/build), process/repo gates y Rust condicional al diff; **no** Playwright.
- `scoped-ci.yml` es manual/reusable y hoy sólo corre `npm run test:desktop:draft-lifecycle`; no una suite Phase12, ni está compuesto en `CI required`.
- `supabase-local` se dispara por paths y está explícitamente fuera de `required.needs`; un fallo no bloquea merge.
- `release-desktop.yml` corre en tag `app-v*`/dispatch, version alignment→build/sign→publicación. No tiene jobs de tests/replay/browser ni evidencia WKWebView antes de upload. Por tanto hoy **no** existe el set transversal que se corra y bloquee cada release.
- Rust se dispara por Rust/seam paths: un release con sólo cambios TS de componentes no garantiza replay Rust por ese tag. Release debe ejecutar replay independientemente del path filter de PR.

Propuesta: mantener el gate universal de merge barato, añadir a la ruta de release un gate de capacidades para el mismo SHA: (1) suite unit/integration completa + matrices Phase12 shell web/desktop; (2) replay Rust + Supabase local donde se acredita nube real; (3) Chromium maestro Phase12 y proyecciones/export; (4) construir/firmar artifact candidato; (5) validate bundle + R16 contra candidato/upgrade exacto, evidencia UI aceptación del dueño donde DoD lo exige; (6) publicar sólo con todos los `needs` aprobados y registro de evidencia. El candidato puede cargarse como artifact interno antes de aprobación; upload a release público queda al final. No inferir que `validate:desktop` ya implementa R16.

Persistir una matriz release trazable `kind × surface × runtime` conectada al registry y a estos escenarios; writer habilitado requiere cada celda anunciada con test observable. CI debe fallar por kind nuevo sin cobertura ejecutable, no sólo por añadir una string al manifest. Matriz DoD 1→R01/R12, 2→R03/R08/R09, 3→R04/R09/R10, 4→R10/R11/R13/R14, 5→R06/R07/R16, 6→R11/R12/R15, 7→R08/R12/R16, 8→artefactos/master demo+aceptación. Integrar first slice antes de habilitar pendientes; no posponer pruebas al issue de cierre.

Orden de implementación recomendado de pruebas: extender ODE-604/606/542 con Card+compuesto y ownership scheduling (R01/R03/R05/R06), browser de Card clean/edit toggle y popover (R02/R04), pérdida/fs/sync/reopen y opaque/migration (R07/R08/R12), después tests por cada kind pendiente y surfaces/export (R09–R15), finalmente wiring release y DMG exacto (R16). ## Construcción de proofs y reducción de la matriz

Aplican `workflow/quality/capability-proof-contract.md` y metodología de `capability-integration-map.md`. Por escenario escribir Proof Contract con capability/failure mode, entry point productivo, cadena real crítica, precondiciones producidas por esa cadena, runtime/dobles, evento terminal, oráculos, carrera de identity/generation y mutante. Si una operación recuperable absorbe una excepción, afirmar independientemente su resultado durable: que el wrapper retorne no prueba que actualizó manifest ni queue. Derivar `coverage_status` al terminar la evidencia, no pedir como objetivo subirla a INTEGRATION. Read-only recon no cambia estados del map. El inventario normativo tiene snapshot antiguo y actualizaciones por fila: comprobar cuerpos de tests y SHA integrado, no heredar cada Status sin revisar.

No ejecutar el producto cartesiano de cada atributo×componente×superficie×estado. Clases de equivalencia: marks (Annotation con proyección/cloud e IDs, Entity con identity repetida, Highlight sin identity, ProtectedText con guard); NodeViews simples (Card con menú/attrs, Tip/Info sin menú complejo); CodeBlock/Mermaid (opaque source/async SVG); grupos (Tabs/Accordion interacción, Steps orden). Cada kind tiene un round-trip contract y cobertura projection declarada; flujos comunes usan representante por clase, mientras el fallo histórico Card y cada owner async/identity distinto conservan caso propio. Si un grupo comparte realmente owner, probar éxito común y diferencias del contrato; no asumir equivalencia sólo por usar NodeView.

Si el mutante queda verde, ajustar proof o declarar límite. No realizar mutantes sobre release distribuido sin checkout aislado y reversión verificable.

### Riesgos adicionales del recon de rama integrada

El coordinador identificó dos riesgos específicos que deben añadir casos dirigidos, sin dar por probado su efecto hasta reproducirlos:

- `acceptedMarkdownForAnnotations`: el setter observado se actualiza desde panel accepted y Rich→Source; probar edición **en Source** seguida de save/hydration/remount y cambio A→B antes de projection. Contrastar anotaciones extraídas con el snapshot actual confirmado, no con raw source cacheado de revisión anterior. Con source estructuralmente inválido, conservar anotaciones previas; al corregirlo y aceptar snapshot válido, proyectar contenido actual exactamente una vez. Extender R03/R08/R12.
- Selección Source cacheada de footnote sin guard `writingId`: capturar selección en A, pasar B y aplicar/confirmar diálogo; B no recibe footnote/rango A y A no se guarda bajo identidad B. Control positivo: selección vigente de B sí inserta y persiste nota. Reabrir ambos para comprobar aislamiento durable. Extender R05 además de los componentes nuevos, pues el cambio transversal puede afectar Markdown existente.

Runtime de comandos: `package.json` exige **Node 22**; usar el mismo Node 22/npm lockfile en validación local y CI. Registrar versión efectiva antes del run.
